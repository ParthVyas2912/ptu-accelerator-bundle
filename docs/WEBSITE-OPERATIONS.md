# Stakeholder website operations

## Purpose and boundary

The stakeholder website is a **public, static, informational** view of the portfolio. It has no API, authentication credentials, model access, data upload or control connection to the accelerator lab. It does not spend PTUs when someone visits it.

- Website: https://ai-solutions-hub-ca.azurewebsites.net/ (branded address)
- Website: https://blue-beach-0fb8cd70f.5.azurestaticapps.net/ (original address, still live)
- Private source: https://github.com/ParthVyas2912/ptu-accelerator-bundle
- Azure resources: `ptu-bundle-portal` (Static Web App) and `ai-solutions-hub-ca` on plan `asp-ai-solutions-hub` (App Service), both in group `rg-ptu-bundle-web`
- Hosting: Azure Static Web Apps **Free**, East US 2; App Service **Free (F1)**, Canada Central
- Provisioning template: `infra/website.bicep`
- Production deploy workflow: `.github/workflows/deploy-site.yml`

Azure Static Web Apps did not offer a Canadian resource region in the provider inventory used for this deployment. East US 2 hosts only curated public-safe material. This is not a Canadian data-residency or DND accreditation claim.

## Website address

`blue-beach-0fb8cd70f` is **auto-generated by Azure, not chosen by us.** The Azure resource is already named `ptu-bundle-portal`; the default hostname is assigned randomly at creation and is independent of the resource name.

Three things follow, and they constrain what a rename can achieve:

- **The default hostname cannot be renamed.** There is no supported operation to change the random portion.
- **Renaming the Azure resource does not change it.** The two are unrelated.
- **Deleting and recreating the site produces another random hostname** — equally off-brand — and invalidates the deployment token, the published links and the recorded publication evidence. Recreation is not a rename, and it is not worth doing for this reason alone.

**Custom domains are the only supported way to add a branded address, and they are additive.** The default hostname is not replaced, redirected away or retired — it keeps serving the site permanently. A branded address sits *on top of* it, so both work. Free tier allows **up to two** custom domains, which is enough for an apex plus `www`, or for two different branded names.

There is no way to obtain a second `*.azurestaticapps.net` name, or to choose the wording of the existing one.

### The branded address that is live today

The lab owns **no DNS zone**, so no custom domain was available. An App Service hostname is a workable substitute because, unlike the Static Web Apps hostname, the name is **chosen rather than generated**:

**https://ai-solutions-hub-ca.azurewebsites.net/**

- `ai-solutions-hub` alone is already taken globally; `-ca` marks the Canadian context.
- The **Free (F1)** plan costs nothing and reserves no compute, so the existing allowances stay closed. No SKU change, no purchase, no quota increase.
- F1 quota was **0 in East US 2**, so the plan runs in Canada Central. It serves a byte-identical copy of the same public file, so this is **not** a data-residency claim.
- It is **additive**: the Static Web App keeps serving its original address unchanged.
- `site/dist/web.config` is generated by `site/scripts/build.mjs` from the same header definition as `staticwebapp.config.json`, so **both addresses serve one security policy from one source of truth**. A build test enforces that they stay in step.
- Basic publishing credentials are disabled by policy on this app and were **not** re-enabled; publishing uses a Microsoft Entra token against the Kudu publish API.

Publishing the same build to this host:

```powershell
npm run build --prefix site
# stage index.html and web.config only, then zip them
$token = az account get-access-token --resource https://management.azure.com/ --query accessToken --output tsv
Invoke-WebRequest -Uri "https://ai-solutions-hub-ca.scm.azurewebsites.net/api/publish?type=zip&clean=true&restart=true" `
  -Method Post -Headers @{ Authorization = "Bearer $token" } -InFile $zip -ContentType "application/zip"
```

Keep `staticwebapp.config.json` out of that zip: App Service would serve it as a file, and it is the Static Web Apps host that needs it.

**Known limitation.** On the Free tier the shared CPU is slow enough that the heaviest deployed browser check — five viewports plus two accessibility scans — can exceed the fixed 120-second per-check deadline in `site/tests/browser.mjs`. Every other deployed check passes, including all private-path exposure checks. Record that result honestly as a timeout rather than a content failure, and confirm it against the Static Web Apps address, which is not CPU-constrained.

### If a real custom domain is approved later

A custom domain remains the better long-term answer, and it can be added to the Static Web App without disturbing either address above.

### Prerequisites before any change

A custom domain needs a domain this work is actually entitled to use. That is an approval question, not a technical one:

- A Microsoft-owned domain or subdomain requires corporate domain and DNS approval; it also makes the site look more official than a private working collection should. Confirm that positioning is intended before requesting it.
- Registering a new domain is a **purchase** and is outside the existing allowances. Do not register one to resolve a naming preference without a funding and ownership decision.
- Whoever owns the domain must be able to create the DNS records and to keep owning them for the life of the site.

Until a domain is agreed, the visitor-facing brand is already **AI Solutions Hub** — in the page title, the heading and the printed output — and the branded App Service address above carries it in the URL too. Only the original Static Web Apps address remains off-brand, and it stays live deliberately.

### Applying a custom domain once a domain is approved

Free tier includes up to two custom domains and managed TLS certificates, so this does not change the SKU or the cost boundary.

1. Create the DNS record with the domain owner **first**; the Azure validation fails otherwise.
   - Subdomain: `CNAME` pointing to the current default hostname, validated with `cname-delegation`.
   - Apex domain: `ALIAS`/`ANAME` or `A` plus the validation `TXT` record, validated with `dns-txt-token`.
2. Redeploy `infra/website.bicep` with `customDomains` set, using the guarded invocation pattern below. The parameter defaults to an empty list and is a no-op when unset. One or two entries are accepted:

   ```json
   [
     { "name": "ai-solutions-hub.example.ca", "validation": "cname-delegation" },
     { "name": "example.ca", "validation": "dns-txt-token" }
   ]
   ```

3. Wait for the managed certificate to issue, then confirm HTTPS on each new address.
4. Update the recorded address in the places that carry it forward:
   - `README.md` (two links)
   - `docs/WEBSITE-OPERATIONS.md` (this file)
   - `docs/website-deployment.json` (`publicUrl`)
   - `site/README.md` (smoke-test examples)
   - `site/tests/public-contract.mjs` (`deployedURL`; a test constant and allowlist entry, not rendered into the site)
5. Re-run the deployed smoke test against the new address.

**Do not rewrite the hostname inside `evidence/`** or inside dated presentation material. Those record what was verified at the time; a later address does not change what was observed.

## Cost

The new Azure resource is a Free-tier static website. The additional branded address runs on a **Free (F1)** App Service plan, which also has no charge and reserves no compute. No additional storage account, database, model deployment, registry, Container App, application backend or paid plan was provisioned for either address. Free-tier limits and GitHub Actions plan allowances apply. The separate retained accelerator lab may still incur its previously documented costs.

Do not change the SKU or add APIs/custom infrastructure without reviewing the new cost and publication boundary.

## Updating the website

1. Create a branch.
2. Edit the curated source under `site/`; never import root reports/evidence into the public build.
3. Follow `site/README.md` to install dependencies, run tests and build.
4. Run the staged publication check: `python scripts/check_publication.py --staged --allowlist scripts/publication_allowlist.json`.
5. Open and review the pull request. Public-content review is required even though the repository is private.
6. Merge into `main`. Changes to `site/` or the deployment workflow trigger the production deployment.
7. Verify the workflow completed, the expected text is live, browser interactions work, and private artifact paths are not exposed.

Historical lab scripts are not a generic validation command. Site work does not authorize inference or lab restarts.

## Deployment credential

`AZURE_STATIC_WEB_APPS_API_TOKEN` is stored as a GitHub Actions secret, never in a file or Git history. It is limited to this static site and is used only by the production deploy job. Workflow permissions default to read-only, Actions are pinned to reviewed commits, pull requests do not receive deployment credentials, and checkout does not persist Git credentials.

Private-repository branch protection requires a GitHub plan feature unavailable on this account at setup. The repository was not made public and no upgrade was purchased. The publish job does not depend on paid environment-protection features; code-owner/PR review is a documented maintainer practice rather than an enforced branch gate.

Do not log the Azure CLI's deployment-token output. To rotate, use the owning Azure resource's token-management operation and immediately update the GitHub secret from process memory or secure stdin. Coordinate rotation with a deployment window. No tenant application registration or client secret is required by this hosting path.

## Rollback

Revert the offending **site source** commit through a reviewed change, run checks, and deploy the resulting `main` revision. A revert of documentation alone does not alter the deployed website.

Do not run destructive lab cleanup, change existing application's ingress, or delete unrelated resources as a website rollback.

## Provisioning again

Infrastructure is intentionally not auto-provisioned by GitHub Actions. Review the target subscription, resource group, region and Free SKU first. Use the guarded Azure invocation pattern for this MCAPS workspace:

```powershell
.\Invoke-LabAz.ps1 deployment group create `
  --name stakeholder-website `
  --resource-group rg-ptu-bundle-web `
  --template-file infra\website.bicep `
  --subscription <approved-mcaps-subscription-id>
```

The guard enforces the subscription in the local deployment contract. This example is not approval to create resources in a different tenant, modify protected applications, or restart model-consuming services.

## Verify resource versus content

An Azure resource returning HTTP 200 may still display the platform's default welcome page. Completion requires both:

1. Resource exists with SKU **Free** and only the intended static-site resource in its group.
2. The built portfolio content is published, interactions pass, and private files are inaccessible.

Final publication evidence is recorded in `docs/website-deployment.json`. Keep operational metadata private; it is not input to the website build.
